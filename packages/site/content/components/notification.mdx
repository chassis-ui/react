## Overview

Things to know when using `Notification`:

- It works standalone — render `<Notification>` directly and control it with `visible`/`onClose`, same as any other component.
- Or push it into a stack — call `addNotification()` from anywhere to queue one, and render a `<NotificationStack>` wherever it should appear. See [Stacking](#stacking).
- `role="status"` (the default) suits routine confirmations and informational updates. Reserve `role="alert"` for errors and messages requiring immediate attention. See [Accessibility](#accessibility).

### Notification icon

Render `<NotificationIcon>` as a child to add a leading icon sized and colored from the component's design tokens. Its presence switches the notification to a two-column grid — the icon in the first column, the message in the second — vertically centered by default. For multi-line messages, add `className="align-self-start"` to the icon so it aligns with the first line of text instead. `NotificationIcon` accepts the same props as `Icon` (`name`, `size`, `font`, `title`, `sprite`) and is hidden from assistive technology by default, since it duplicates the message visually — see [Accessibility](#accessibility).

## Stacking

For notifications created at runtime — in response to a save, an upload, an error — call `addNotification()` from anywhere: an event handler, an async callback. It returns a key you can pass to `closeNotification()` to dismiss it programmatically. `NotificationStack` subscribes to the same shared queue and renders whatever's currently in it; nothing else needs to know about it — pass `dismissible` in the options and its close button removes it from the queue on click, same as any other notification.

<Example>
  <LiveExample client:load />
</Example>

`NotificationStack` doubles as a plain grouping wrapper, too — pass `<Notification>` elements to it directly as `children` and it just adds spacing between them, no queue required. Combine both: static children render first, followed by anything queued.

By default, the most recently queued notification renders first — the typical toast pattern. Pass `reverse` for a chronological transcript instead, oldest first.

## Accessibility

`Notification` renders with `role="status"` by default — an implicitly polite live region suited to confirmation, progress, and informational messages ("Saved", "Upload complete"). For messages that need **immediate** attention — validation errors, failed operations, lost connection — pass `role="alert"` instead, which interrupts the screen reader rather than waiting for a pause. Pick the role from the message's urgency, not its color: a `danger` notification reporting passive state can stay `status`, and an `info` notification demanding an immediate response should be `alert`.

`<NotificationIcon>` is hidden from assistive technology (`aria-hidden`) by default, since it duplicates the adjacent text visually and shouldn't be announced separately. Pass a `title` if the icon ever needs to convey information the text doesn't.

Place the close button as the **last** child even when it's visually pinned to the top-right corner — `dismissible` already does this for you, appending its `CloseButton` after `children`. Because `status` and `alert` are both implicitly `aria-atomic`, the whole notification is announced as one unit, so close-last means the message is read before the dismiss control, and it's also the last stop in tab order.

Dismissing a notification unmounts it, which can leave keyboard focus orphaned. Move focus in `onClose` — to the control that triggered the notification, the next one in a stack, or the main content landmark.
