## Overview

The navbar is the primary navigation surface for a site or application. It composes a branding area, a set of navigation links, optional forms or text, and a drawer-based mobile menu — all wrapped in a single `<nav>` element (rendered by `<Navbar>`) that is responsive by default.

`<Navbar>` accepts a handful of sub-components as needed: `<NavbarBrand>` for a project or product name, `<NavbarNav>` for navigation links, `<NavbarToggler>` for opening the mobile `<Drawer>`, `<NavbarText>` for inline text, and standard form components for search boxes or other controls.

## Basic usage

A complete navbar combines a `<NavbarBrand>`, a `<NavbarToggler>`, and a `<Drawer>` that holds the navigation below the `expand` breakpoint. The `expand` prop controls when the drawer's contents flow inline instead — set on a container-query basis, so the transition responds to the navbar's own width rather than the viewport width.

## Responsive behavior

The `expand` prop controls when the navbar transitions between drawer mode and inline mode, implemented with container queries so the transition responds to the navbar's own width:

- `expand="small"` — drawer below the small breakpoint, inline at small and above
- `expand="medium"` — drawer below medium, inline at medium and above
- `expand="large"` — drawer below large, inline at large and above
- `expand="xlarge"` — drawer below xlarge, inline at xlarge and above
- `expand="2xlarge"` — drawer below 2xlarge, inline at 2xlarge and above
- `expand={true}` — inline at all widths (toggler hidden, drawer contents render flat inside the navbar)
- `expand` omitted — drawer at all widths (toggler always visible, the drawer must be opened to access the nav)

## Toggle button

`<NavbarToggler>` has no fixed position — its location within the navbar is determined by its order in the markup relative to other flex siblings. Placing it before `<NavbarBrand>` renders it on the left; placing it after renders it on the right. The flex container distributes spacing between siblings automatically, so no positioning utility classes are required.

## External content

`<Drawer>` and `<NavbarToggler>` are only linked by the `visible`/`onClose`/`onClick` state a consumer wires between them, so the controlled drawer can live anywhere in the document — not necessarily inside `<Navbar>`. Use this when the controlled content is structurally separate from the navigation surface.

<Callout type="warning">
  When the controlled drawer precedes its toggler in document order, keyboard and assistive technology users may have trouble locating the newly revealed content. Move focus into the drawer on open (`<Drawer>` does this automatically), and keep `aria-controls` pointing at the drawer's `id` so the toggler-to-content relationship is exposed.
</Callout>

## Accessibility

An accessible navbar relies on semantic markup and ARIA attributes that assistive technologies can interpret.

- `<Navbar>` renders a `<nav>` element by default, exposing it as a landmark region. Pass an `aria-label` when a page has more than one navbar.
- Mark the current page with `active` on the relevant `<NavLink>`, which renders `aria-current="page"`.
- `<NavbarToggler>` doesn't sync its ARIA attributes automatically — unlike the underlying CSS framework's vanilla JavaScript plugin, this component is a plain controlled button. Set `aria-label`, `aria-controls` (pointing at the drawer's `id`), and `aria-expanded` (kept in sync with the `Drawer`'s own `visible` state) explicitly, as every example above does.
