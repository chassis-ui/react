## Overview

`<FormField>` wraps a form control (or a small group of them) with a `.form-field` grid layout, along with an associated `FormLabel`, `FormHelp`, and `FormFeedback` — see [chassis-css's Form Field docs](https://chassis-ui.com/css/docs/forms/form-field) for the underlying CSS.

Every field component (`TextInput`, `Textarea`, `Select`, `RangeInput`, `FileInput`, `ColorInput`, `Combobox`, `Autocomplete`, `DatePicker`, `DateRangePicker`, `TimeField`, `NumberField`, `SearchField`, `ChipInput`, `OtpInput`) already accepts `label`/`help`/`invalidFeedback`/`validFeedback` props directly, lays itself out the same way and wires the label, help and feedback to its control — reach for those first, and don't wrap one of them in `<FormField>` to label it. Use `<FormField>` for what they can't do: a control with no field props of its own, like an `<InputGroup>`, or more than one element — like an input alongside a `PasswordStrength` meter — under a single label and help text.

`<FormField>` renders nothing but its `children` bare when none of `label`/`help`/`validFeedback`/`invalidFeedback` are set, so it's always safe to reach for.

### Wrapping a control

### Validation feedback

`invalidFeedback`/`validFeedback` render only alongside a truthy `invalid`/`valid`, matching the leaf components' own validation props. `<FormField>` never changes its children, so set `invalid`/`valid` on the control too: its state is what shows the feedback and draws its border. Point the control's `aria-describedby` at `ids.feedback` so the message is read with it.

## Manual id wiring

`<FormField>` doesn't clone its children, so it can't wire ids onto a control it doesn't own. Without the wiring the label and help are only text beside the control: a screen reader announces neither with it. Choose the ids, pass them through the `ids` prop, and repeat them on the control:

| `ids` key  | `<FormField>` puts it on          | Set on the control                         |
| ---------- | --------------------------------- | ------------------------------------------ |
| `input`    | the label, as `htmlFor`           | `id`                                       |
| `label`    | the label, as its own `id`        | `aria-labelledby`                          |
| `help`     | the help text, as its `id`        | `aria-describedby`                         |
| `feedback` | the feedback message, as its `id` | `aria-describedby`, while the state is set |

Which of `input` and `label` to use depends on the control:

- A native `<input>`, `<select>` or `<textarea>`, or a `<Select>`, needs `input` only.
- A `<TextInput>` or `<Textarea>` takes both. `input` is enough to name it, but react-aria, which these are built on, reads only the control's own `aria-label`/`aria-labelledby`, and warns in development about a field it finds neither on.
- A group with no single input to target, like a `role="group"` element, takes `label` only: `htmlFor` does nothing on an element that isn't a form control.

A control's own `aria-label` wins over both. `<ChipInput>` falls back to one (`"Add value"`) unless it gets `label`, `aria-label` or `aria-labelledby`, which is one more reason to pass `label` to it rather than wrap it.
