## Overview

`<Nav>` shares its base markup and styling — the `.nav` class, active and disabled states — across
plain, tabbed, and pilled navigation. Swap the `variant` prop to switch between styles without
changing the surrounding markup.

## Basic usage

`<Nav>` is built with flexbox and provides the foundation every style variant below builds on: some
style overrides for working with lists, link padding for larger hit areas, and disabled styling.
Compose it from `<NavItem>`/`<NavLink>` pairs, mark the current link with `active`, and mark an
unavailable one with `disabled`.

<Example>
  <BaseNavExample client:load />
</Example>

The `<NavItem>`/`<NavLink>` pairing is optional. Since `.nav` uses `display: flex`, rendering
`<Nav component="nav">` with direct `<NavLink>` children behaves the same way, without the extra
markup.

</Example>

## Alignment and layout

Flexbox utilities control a nav's horizontal alignment, stacking, and how its items fill the
available width. Mix and match as needed.

### Horizontal alignment

Navs are left-aligned by default. Apply `.justify-content-center` to center them:

<Example>
  <CenteredExample client:load />
</Example>

Or `.justify-content-end` to right-align them:

<Example>
  <RightAlignedExample client:load />
</Example>

### Vertical stacking

Apply the `.flex-column` utility to stack nav items vertically instead of horizontally. Use a
responsive variant (e.g. `.small:flex-column`) to stack only below a given breakpoint.

<Example>
  <VerticalExample client:load />
</Example>

### Fill and justify

Two modifier classes extend a nav's contents to the full available width. `layout="fill"`
proportionately fills all available space with `.nav-item`s — every item occupies the horizontal
space, but not necessarily at equal widths.

<Example>
  <FillExample client:load />
</Example>

`layout="justified"` instead gives every nav item an equal width, filling the same available space.

</Example>

## Accessibility

When using `<Nav>` to provide a navigation bar, add `role="navigation"` to the most logical parent
container, or wrap a `<nav>` element around the whole navigation — not the `<ul>` itself, since that
would prevent it from being announced as an actual list by assistive technology.

A navigation bar, even one visually styled as tabs via `variant="tabs"`, shouldn't be given
`role="tablist"`, `role="tab"`, or `role="tabpanel"` attributes. Those are only appropriate for
dynamic tabbed interfaces, as described in the
[<abbr title="Web Accessibility Initiative">WAI</abbr> <abbr title="Accessible Rich Internet Applications">ARIA</abbr> Authoring Practices](https://www.w3.org/TR/wai-aria-practices/#tabpanel).
`<Nav>` itself only renders the `nav`/`nav-tabs`/`nav-pills` styling and has no notion of a selected
panel to wire up — reach for [`Tabs`](./tabs) instead, which handles the full
`role="tablist"`/`role="tab"`/`role="tabpanel"` + `aria-selected`/`aria-controls`/`aria-labelledby`
pattern, keyboard navigation, and animated panel switching.
