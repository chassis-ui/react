## Overview

Things to know when using `Notification`:

- It works standalone — render `<Notification>` directly and control it with `visible`/`onClose`, same as any other component.
- Or push it into a stack — call `addNotification()` from anywhere to queue one, and render a `<NotificationStack>` wherever it should appear. See [Stacking](#stacking).
- `role="status"` (the default) suits routine confirmations and informational updates. Reserve `role="alert"` for errors and messages requiring immediate attention. See [Accessibility](#accessibility).
- The `icon`/`title`/`text`/`actions` props are shorthand for the manual `NotificationIcon`/`NotificationTitle`/`NotificationText` composition — reach for manual composition only when a notification needs more than one block of body content. See [Shorthand props](#shorthand-props).
- To dismiss a notification from hand-composed markup — a labeled button in `actions`, instead of (or alongside) the `dismissible` close icon — call `useNotification()` and wire its `close` to any element's `onClick`. See [Dismissing](#dismissing).

### Shorthand props

For the common case — an icon, a heading, one block of message text — `icon`/`title`/`text` render the same markup as composing `NotificationIcon`/`NotificationTitle`/`NotificationText` by hand, without the wiring. `icon` accepts an icon name string (rendered via `NotificationIcon`) or any other node for a fully custom icon; `title` renders through `NotificationTitle` (pass `titleComponent` to change its tag, default `h4`); `text` renders through a single `NotificationText`. When both `title` and `text` are set, the notification's `aria-labelledby`/`aria-describedby` are wired to them automatically.

`text` wraps everything in _one_ `NotificationText` — for multi-block content (more than one paragraph, or content mixing paragraphs with other elements), compose `children` manually instead, as shown in the sections below. `actions` is unstyled passthrough markup rendered after `text`/`children`, e.g. a row of buttons — see [Actions](#actions).

The rest of this page documents the manual composition these props are shorthand for.

### Notification icon

Render `<NotificationIcon>` as a child to add a leading icon sized and colored from the component's design tokens. Its presence switches the notification to a two-column grid — the icon in the first column, the message in the second — vertically centered by default. For multi-line messages, add `className="align-self-start"` to the icon so it aligns with the first line of text instead. `NotificationIcon` accepts the same props as `Icon` (`name`, `size`, `font`, `title`, `sprite`) and is hidden from assistive technology by default, since it duplicates the message visually — see [Accessibility](#accessibility).

Add the `dismissible` prop to render a close button and let users dismiss the notification. `onClose` fires once the fade-out transition finishes. The close button's accessible name defaults to `'Close'` — override it with `closeLabel` for non-English UIs.

Call `useNotification()` from a child of `Notification` and wire its `close` to any element's `onClick`; there's no separate close subcomponent to reach for, the same normal `Button` works.

### Auto-dismiss

Set `autohide` to dismiss the notification on its own after `delay` (defaults to `5000`ms). Unlike `Toast`, `Notification` does **not** auto-hide by default — it's documented as a persistent banner, so opt in explicitly. The timer pauses while the pointer or keyboard focus is on the notification, and resumes when it leaves.

## Stacking

For notifications created at runtime — in response to a save, an upload, an error — call `addNotification()` from anywhere: an event handler, an async callback. It returns a key that can be passed to `closeNotification()` to dismiss it programmatically. `NotificationStack` subscribes to the same shared queue and renders whatever's currently in it; nothing else needs to know about it — pass `dismissible` in the options and its close button removes it from the queue on click, same as any other notification.

<Example>
  <LiveExample client:load />
</Example>

`NotificationStack` doubles as a plain grouping wrapper, too — pass `<Notification>` elements to it directly as `children` and it just adds spacing between them, no queue required. Combine both: static children render first, followed by anything queued.

By default, the most recently queued notification renders first — the typical toast pattern. Pass `reverse` for a chronological transcript instead, oldest first.

## Accessibility

`Notification` renders with `role="status"` by default — an implicitly polite live region suited to confirmation, progress, and informational messages ("Saved", "Upload complete"). For messages that need **immediate** attention — validation errors, failed operations, lost connection — pass `role="alert"` instead, which interrupts the screen reader rather than waiting for a pause. Pick the role from the message's urgency, not its color: a `danger` notification reporting passive state can stay `status`, and an `info` notification demanding an immediate response should be `alert`.

`<NotificationIcon>` is hidden from assistive technology (`aria-hidden`) by default, since it duplicates the adjacent text visually and shouldn't be announced separately. Pass a `title` if the icon ever needs to convey information the text doesn't.

Place the close button as the **last** child even when it's visually pinned to the top-right corner — `dismissible` already does this automatically, appending its `CloseButton` after `children`. Because `status` and `alert` are both implicitly `aria-atomic`, the whole notification is announced as one unit, so close-last means the message is read before the dismiss control, and it's also the last stop in tab order.

Dismissing a notification unmounts it, which can leave keyboard focus orphaned. Move focus in `onClose` — to the control that triggered the notification, the next one in a stack, or the main content landmark.
