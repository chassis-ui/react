Every form component accepts `invalid`/`valid` booleans plus `invalidFeedback`/`validFeedback` text
— see [Working with Forms]([[docsref:/getting-started/working-with-forms]]) for that shared prop
surface. This page covers the four ways that state actually reaches the screen — browser-default
tooltips, custom Chassis styling, predetermined server-side state, and compact inline tooltips —
plus the opt-in validation icon and which components support each.

## Browser defaults

With no extra configuration, a `<Form>` relies on the browser's own constraint validation: a form
with an invalid field, such as an empty `required` one, isn't submitted, and its first invalid field
takes focus. Every field that held the form back then shows as invalid, with its `invalidFeedback`
if it has one, until it no longer would or the form is reset. Set `invalid` on a field, to `false`
too, and that prop alone decides how it looks.

The browser's own message, a native tooltip beside the first invalid field, appears only on a field
that is a plain native control: `Select`, `FileInput` and a `Switch` with `type="radio"`. The other
fields are built on react-aria, which cancels it. Its text comes from the browser, though it can
still be customized in JavaScript via
[`setCustomValidity()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/setCustomValidity),
and it can't be styled with CSS. Reach for [Custom styles](#custom-styles) when a design needs
Chassis's own feedback styling for every state.

## Custom styles

Set `noValidate` on `<Form>` to disable the browser's default feedback UI while still keeping the
Constraint Validation API available in JavaScript. The example below intercepts `onSubmit`, stops
the submit while `form.checkValidity()` is false, and sets `validated` on `<Form>` once the user has
attempted to submit, so no field shows as invalid before the user has done anything.

With `validated` set, every field in the form shows itself as valid or invalid by its own
constraints (`required`, `type`, `pattern`, `minLength` and the like), and again as its value
changes: its colors, `aria-invalid`, and its `validFeedback` or `invalidFeedback`. A field's own
`invalid` or `valid` still decides how that field looks, for what the browser can't check, such as
a username that is already taken.

A `FormFeedback` composed beside a control, as the username field does, shows once its control is in
the matching state. A control that isn't one of this library's components, such as a plain
`<input className="form-input">`, isn't affected by `validated`: set `.is-valid` or `.is-invalid` on
it. Chassis CSS's own native validation styles, opted into with a `data-cx-validate` attribute on
the form (see chassis-css's [Form Validation](https://chassis-ui.com/css/docs/forms/validation)
page), style such a control too, but they also restyle this library's fields by the browser's
verdict alone, over a field's own `invalid` or `valid`, and never show its feedback text.

## Server-side

When validity is already known ahead of time — a server response, a prior submit attempt — set
`invalid`/`valid` directly instead of relying on native constraint validation. No `noValidate` or
submit handler is needed; the state renders as soon as the props are set.

<Callout type="warning">
  A control's own `invalidFeedback`/`validFeedback` prop wires `aria-describedby` automatically.
  Composing a control manually alongside an `InputGroup` or a standalone `FormFeedback` — as the
  username and terms fields below do — means wiring `aria-describedby` to the feedback text's `id`
  by hand instead. `aria-describedby` accepts more than one id, so reference an addon and a
  feedback message together (see the username field).
</Callout>

## Supported elements

Base validation styling — state colors, border, focus ring, and feedback text — works on every
form component: text-like inputs, `Select`, `Textarea`, the toggle family (`Checkbox`, `RadioGroup`,
`Switch`), `FileInput`, `ColorInput`, `RangeInput`, `ChipInput`, `Combobox`, `InputGroup`-composed
fields, adorned inputs, and `FloatingInput`. A `multiple` `Select` still picks up the color/border
styling — only the [validation icon](#validation-icons) is narrower than this list.

## Validation icons

Add the `validation-icons` class to any ancestor — typically `<Form>`, but a `.form-field`,
`InputGroup`, or a single control works too — to render a success or error glyph inside every
supported descendant once it enters a validation state. Without that ancestor class, inputs still
pick up validation colors, border, and feedback text; only the icon is omitted.

The icon renders on text-like inputs, a single-value `Select` (not `multiple`, and not a `size`
greater than `1`), `ColorInput`, ghost-input-based controls (`ChipInput`, and any `TextInput`/
`Select` using `adornStart`/`adornEnd`), and `Combobox`. `Textarea`, `Checkbox`, `RadioGroup`,
`Switch`, `FileInput`, and `RangeInput` never render one, by design — and a disabled control never
shows the icon even when it's otherwise eligible.

## Tooltips

For compact layouts, swap `FormFeedback`'s block-style feedback for a positioned tooltip by
passing it `tooltip` instead of relying on a control's own `invalidFeedback`/`validFeedback` shorthand
— that shorthand always renders the block style, so a tooltip needs `FormFeedback` composed
manually alongside a bare control, the same way the username field on this page composes
`InputGroup`. The tooltip positions itself against the nearest ancestor with `position: relative`
— add `.position-relative` to the element around the control, as each `<GridItem>` does here.
